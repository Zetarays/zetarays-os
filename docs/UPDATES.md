# Updating ZETA RAYS without reinstalling

Two ways, for two moments:

| | A. Upgrade file | B. Software Update (APT repository) |
|---|---|---|
| For | ZETA RAYS 2.5 systems moving to 3.0 | ZETA RAYS 3.0 and later, for every update after it |
| What the user does | runs one file, once | nothing special: Settings › Software Update |
| Built by | `tools/make-upgrade.sh` | `tools/make-zeta-debs.py` + `tools/make-apt-repo.py` |
| Published at | next to the images (`download.zetarays.org/releases/3.0/`) | `https://zetarays.org/apt/` |

Debian packages keep updating from the Debian servers on every version, as
before; both paths are about the ZETA RAYS components themselves.

---

## A. The upgrade file (2.5 to 3.0)

### Building it

```
tools/make-upgrade.sh            # both architectures
tools/make-upgrade.sh arm64      # one
```

Output: `out/zetarays-3.0-upgrade-amd64.run` and `-arm64.run` (about 25-35 MB
each), each with a `.sha256` file. One file per architecture because of the
AI engine; everything else is the same.

It runs the same generation steps as `build.sh` (translations, assets,
Firefox start page, boot theme), then `tools/upgrade/make_bundle.py`, which
compares the released 2.5 configuration (`.cache/src-2.5-release-config`,
read-only) with the current tree and packs:

- the ZETA RAYS files of `includes.chroot` (the list and the rules are in
  `tools/upgrade/zeta_files.py`): everything under `/usr` that ZETA RAYS
  ships, `/etc/skel`, and the ZETA RAYS files in `/etc`. Left out: AI models,
  files of the live session (`live-config`), the installer (Calamares
  removes itself from installed systems), inputs of the build hooks;
- `ollama.service` as hook 0300 writes it, and the extra package sources of
  `config/archives`;
- the list of packages added to `config/package-lists` since 2.5 (computed
  per architecture, `#if ARCHITECTURES` blocks included) and the
  `systemctl enable/disable` lines added to the hooks since 2.5;
- the Ollama runtime from `cache/ollama-linux-ARCH.tar.zst`, without the GPU
  libraries (hook 0300 removes them from the image too): about 60-120 MB
  unpacked instead of 2 GB;
- the build hooks that the upgrade runs again (`0500` menu, `0600` legal
  documents, `0650` security scans);
- the patched Hyprland packages and hooks 0350/0400 only if the patched
  Hyprland differs from the one 2.5 installed (today it does not);
- `zeta-rays-release` (path B's package source), if the repository key exists;
- SHA-256 checksums: of the whole payload (checked before anything else) and
  of each file in it.

**Reviewed hooks.** If a build hook changed since it was last reviewed for
the upgrade, `make-upgrade.sh` stops and names it. Read the change and
decide whether the upgrade has to repeat it on an installed system (see the
`how` notes in `tools/upgrade/hooks-reviewed.json`; the code is
`tools/upgrade/zeta_upgrade.py`, function `post_steps`), then run
`tools/make-upgrade.sh --accept-hooks`. This keeps a change made only in a
hook (a new service, a new generated file) from silently missing from the
upgrade.

**User settings.** The changes to `/etc/skel` reach existing users through
`zeta-migrate-user` at their next login: `usr/share/zeta/migration/update-3.0-0-defaults.json`
(generated by `tools/upgrade/gen_migration.py 3.0`) replaces the default
files a user never changed, keeps the changed ones (the new version goes to
`~/.local/state/zeta/migration-new/` for comparison), adds the new files
and, in a changed `hyprland.lua`, appends the new shortcuts in a marked
block (only single-line `hl.bind(...)` lines that use nothing but the `hl`
API and `mod`, each in `pcall`, never a key the user already bound). Other
`update-3.0-*.json` files sort after it and patch only what a user changed.

### Publishing it

Upload both `.run` files and their `.sha256` next to the 3.0 images, in
`download.zetarays.org/releases/3.0/ARCH/upgrade/`. The download section of
the website links them ("Already on 2.5? Upgrade without reinstalling",
`#upgrade`); `tools/sync-site.sh` copies them from `out/` into the delivery
folder if they are not there yet and writes their sizes and checksums into
the page and into `SHA256SUMS`.

### What the user does

From a terminal (recommended):

```
sudo bash zetarays-3.0-upgrade-amd64.run --dry-run   # shows what would change, changes nothing
sudo bash zetarays-3.0-upgrade-amd64.run             # upgrades (asks before starting)
```

From the file manager: right-click the file › Properties › Permissions ›
allow running it as a program, then double-click it and choose Run. A
terminal window opens, the system asks for the administrator password, and
the progress is shown there. At the end it offers to restart.

Messages are in Italian when the session language is Italian, English
otherwise (the table is `tools/upgrade/data/it.json`, built into the file:
the 2.5 translations do not have these texts. Do not merge it into
`po/it.po`: `tools/i18n.py check` would report the strings as stale).

### What it does on the computer

1. **Checks**, nothing changed if one fails: ZETA RAYS 2.5 (`ID=zeta`,
   `VERSION_ID` in `/etc/os-release`; 3.0 is accepted too, see re-runs),
   the architecture, not the live session, free space, the Debian servers
   reachable, no other package manager running.
2. **Backup** in `/var/backups/zeta-rays-2.5-DATE/`: a copy of every file
   that will be replaced or removed (`files/`, listed in `replaced.txt`),
   the list of files that did not exist (`created.txt`), the old Ollama
   runtime, the package list before, and `rollback.sh`.
3. **Packages**: `apt-get update`, the packages new in 3.0
   (`--no-install-recommends`, as the image), then the pending Debian
   updates (`dist-upgrade`). If apt would remove any package, it stops
   first. Hyprland must stay the patched `+zeta` build.
4. **ZETA RAYS files**: `/usr` files replaced; `/etc` files replaced only if
   they are exactly the 2.5 version (or missing because they are new). A
   file changed on the computer (for example the automatic security updates
   switch) stays, and if 3.0 changed it the new version is written next to
   it as `FILE.dpkg-dist` and listed at the end. sudoers and firewall files
   are checked (`visudo`, `nft -c`) before they are installed. Then the
   Ollama runtime (the service is stopped and started again), the version
   (`/etc/os-release`, `/usr/lib/os-release`, `/etc/issue`, `/etc/issue.net`,
   `/etc/motd`; the GRUB theme carries it in the bundle) and the new
   services. If anything in this step fails, the files are put back at once
   (packages installed by apt stay: they work with both versions).
5. **What the hooks do**: `daemon-reload`, schemas, icon caches, menu
   database, precompiled Python, hooks 0500/0600/0650, new locales if
   `languages.json` changed (the user's language is never reset), boot
   splash and initramfs if the boot theme changed, `update-grub` if
   `/etc/default/grub.d` changed, `zeta-rays-release`.
6. **Summary**, log in `/var/log/zeta-rays-upgrade.log`, restart.

The AI model is not in the file (2.5 GB). The model the computer has keeps
working; Settings › AI shows "Recommended for this computer" with the 3.0
model and downloads it with one click.

Not upgraded by the file: the voices and speech models (same as 2.5),
LocalSend (same version). New firewall rules apply after the restart (the
running firewall is not reloaded during the upgrade).

**Running it again** is safe: unchanged files are skipped. If it was
interrupted (window closed, power cut), the next run resumes with the same
backup, so the copies of the 2.5 files are never overwritten.

**Going back**: `sudo bash /var/backups/zeta-rays-2.5-DATE/rollback.sh`, then
restart. It restores the files and the old Ollama runtime and undoes the new
services; packages stay. User settings changed at login have their own
copies in `~/.local/state/zeta/migration-backup/`.

### Testing it in a 2.5 virtual machine

1. Take a snapshot of the 2.5 VM. Copy the file into it (for example
   `scp out/zetarays-3.0-upgrade-arm64.run zeta@VM:`).
2. `sudo bash zetarays-3.0-upgrade-arm64.run --dry-run`: check the lists
   (new files, `.dpkg-dist` candidates, new packages, Ollama).
3. `sudo bash zetarays-3.0-upgrade-arm64.run`, answer `y`.
4. Check: `cat /etc/os-release`, `tail -50 /var/log/zeta-rays-upgrade.log`,
   `ls /var/backups/`, `ollama --version`, `systemctl status ollama`,
   `apt-cache policy zeta-rays-release`.
5. Restart, log in, then `cat ~/.local/state/zeta/migrated-update-3.0-0-defaults`
   and `zeta-selftest system` (`zeta_updates_source`,
   `upgrade_record_consistent`, `user_migrations_valid`, `no_failed_units`).
6. Run the file again: "0 new, 0 changed".
7. `sudo bash /var/backups/zeta-rays-2.5-*/rollback.sh`, restart: 2.5 again.
8. From the file manager: double-click (after allowing it to run): the
   terminal window and the password dialog must appear.

The upgrade logic can also be tried without a VM, on a copy of a system
tree: `bash FILE.run --root=/some/dir --dry-run` (no root needed; apt and
system commands are only printed).

## B. Updates through Software Update (APT repository)

### How it fits together

- **`zeta-rays-release`** (built by `tools/make-zeta-debs.py --release-only`):
  the source `/usr/share/zeta-rays-release/zeta-rays.sources` (deb822,
  `https://zetarays.org/apt/`, suite `trixie`, component `main`, `Signed-By`
  the key below), `/usr/share/keyrings/zeta-rays-archive-keyring.gpg`, and
  `/usr/share/zeta-rays-release/check-source`, run by APT before every update
  (`/etc/apt/apt.conf.d/50zeta-rays-source`) and by the package's postinst.
  The check copies the source to `/etc/apt/sources.list.d/zeta-rays.sources`
  only while `https://zetarays.org/apt/dists/trixie/InRelease` answers and
  removes it otherwise: a repository that is not published yet (or a site
  that is down) never makes `apt update` and Software Update fail. APT reads
  its sources before the check runs, so a change applies from the next update.
  The 3.0 image installs the package (hook 9993, after the final package
  upgrade, so the image build never reads that source), and so does the 2.5
  upgrade file. `zeta-apt-sources` (installer step) runs the check too.
- **`zeta-rays-desktop`** (built by `tools/make-zeta-debs.py`): the same
  files as the image (`tools/upgrade/zeta_files.py`, the same list the
  upgrade file uses). Files with ZETA in their name and `/etc/skel` belong to
  the package (`/etc` ones as conffiles); files that a Debian package may
  also ship (`/etc/nftables.conf`, `/etc/default/earlyoom`...) are stored in
  `/usr/share/zeta-rays-desktop/files/` and copied by `postinst` with the same
  rule as the upgrade file (replaced if unchanged, otherwise `.dpkg-dist`).
  `postinst` also rebuilds schemas, icon caches, the menu database and the
  precompiled Python.
- **The 3.0 image does not install `zeta-rays-desktop`**: its files come from
  `includes.chroot` as before. Making the whole image a package would change
  how every file reaches the image a few days before the release; the
  package is built and published, and becomes the path for 3.0.x/3.1:
  Software Update shows updates only for installed packages, so the next
  release ships `zeta-rays-release` with `Depends: zeta-rays-desktop (>= X)`.
  That update appears in Software Update on every 3.0 system and pulls in
  the desktop package, which from then on updates like any other package.
  dpkg overwrites the files `includes.chroot` put there (they belong to no
  package). Before doing that, test `dpkg -i zeta-rays-desktop_*.deb` on a
  3.0 VM: `dpkg-deb -c FILE | awk '{print $6}' | sed 's#^\./#/#' | xargs -r dpkg -S 2>/dev/null`
  must list no file of another package.
- Software Update (PackageKit) needs no change: it lists updates from every
  configured source.

### The signing key

```
tools/apt/gen-repo-key.py          # once; prints the fingerprint
```

- Private key: `~/RAiX/.cache/v30/repo-key/private-ed25519.pem` (folder 0700,
  file 0600). It never goes into the repository, the images or the website.
  **Back it up offline** (two copies): every system that trusts this key can
  only be updated with a signature made by it.
- Public key: `tools/apt/zeta-rays-archive-keyring.gpg` (what apt reads) and
  `.asc` (for people), committed with the sources.
- Format: OpenPGP v4, Ed25519, SHA-512 signatures, written by
  `tools/apt/openpgp.py` (no GnuPG needed on the Mac). Checked by an
  independent parser; to be confirmed once with GnuPG/Sequoia in a VM:
  `gpgv --keyring ./zeta-rays-archive-keyring.gpg InRelease` and
  `sqv --keyring ./zeta-rays-archive-keyring.gpg InRelease`.

### Publishing a release of the packages

```
python3 tools/make-zeta-debs.py                      # out/debs/zeta-rays-{release,desktop}_VERSION_all.deb
python3 tools/make-apt-repo.py --keep-old SITE_COPY  # out/apt/, signed
```

`--keep-old` points to a copy of what is online, so older versions stay in
the pool. Upload `out/apt/` to `https://zetarays.org/apt/` as static files
(any web server; HTTPS; `.deb` as `application/vnd.debian.binary-package`
or `application/octet-stream`; `InRelease`, `Release`, `Packages` as plain
files). Upload the pool first and `dists/` last, so a client never sees an
index that names a file not yet there.

**Release blocker**: publish the repository (at least the 3.0 packages)
before the 3.0 images and the upgrade file go out. Until
`https://zetarays.org/apt/dists/trixie/InRelease` exists, every
`apt-get update` on 3.0 reports an error for that source (Debian updates
still install) and Software Update shows a warning. `make-ova.sh` already
tolerates it while building.

### Checking a published repository from a ZETA RAYS 3.0 VM

```
sudo apt-get update                      # no error for zetarays.org
apt-cache policy zeta-rays-release       # candidate from https://zetarays.org/apt trixie/main
pkcon get-updates                        # a newer zeta-rays-* appears here and in Settings › Software Update
```
